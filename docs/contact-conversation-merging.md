# 联系人消息合并方案（待实现的统一行为）

**现状：** Flutter 的聊天列表已经按本机联系人 ID 合并；消息正文默认显示当前路线，通过联系人详情里的开关合并多个 iMessage 路线。Windows 已按 vCard 的稳定 contact_id 合并列表和多路线正文，并保存发送路线。两端的开关、路线范围和默认行为存在差异。本次修改修复了 Windows 合并会话的逐路线未读聚合，没有改变合并开关或发送路线。

**建议行为：** 保留按稳定联系人 ID 的自动列表分组，在联系人详情提供一致的“合并显示消息”开关。第一次启用时明确列出参与的电话、邮箱和服务，由用户选择范围；群聊独立。正文和媒体共用 `/api/messages/history` 的多路线游标，消息身份使用聊天 GUID 与真实消息 GUID 的组合。预览取所有路线的最新消息，发送使用单独保存的路线，编辑、撤回、隐藏按原消息所属路线执行。输入区显示当前发送目标，用户选择的路线失效时要求重新选择，避免静默切换到另一地址。

**跨设备一致性：** Android 通讯录 ID 与 Windows vCard ID 属于不同来源，不能作为公共同步键。服务端可保存 `serverId + conversationGroupId`、路线 GUID 集合、合并开关和默认发送路线；本机联系人仅负责提供姓名和头像。采用版本检查、离线队列和明确的冲突处理。自动识别可以建议分组；同步后的路线成员关系由服务端记录确定，避免两台设备使用不同通讯录时出现不同分组。

**验收范围：** 同名联系人保持独立；电话、邮箱和 SMS 路线能明确选入或移出；多路线历史分页不漏行、不重复；回复、附件、隐藏和撤回保留原路线；每条路线的已读状态独立维护，合并红点取任一路线未读、未读计数求和；发送路线不因最新来信而自动变化。跨设备已读位置同步仍是单独的后续改动，本次统一 Windows 的本地红点规则。
